# C2000MAX v36.5 排查与验证报告

日期：2026-09-05。源码分支：本地 `v36.5`，基于 `c2000max-v36.10` 的 `d5bb266141` 和本地已有修复继续修改，未推送远端。

## 结论与边界

本轮修复了可在源码、日志或实机中确认的问题，并完成固件构建与静态/模拟回归。没有自动刷写设备。不能据此宣称 Wi-Fi 吞吐、5G 游戏延迟或那位用户的 LAN 卡顿已全部实测解决：目前没有持续在线的 5 GHz Wi-Fi 7 测试客户端，也没有问题现场的拓扑、负载和稳定 5G 上下行测速值。

`kernel.txt` / `log.txt` 来自另一位用户；以下“本机”数据来自通过有线 SSH 连接的 `192.168.66.1`，两组证据没有混用。

## 1. Wi-Fi 性能与驱动

- 对方日志出现 `PeerAssocReqCmmSanity` 的 FORTIFY 告警：旧代码把 35 字节复制到只有 1 字节声明大小的结构体字段，依赖跨字段写入。改为检查 OWE ECDH IE 长度、清零目标，再复制到整个 IE 结构体；没有关闭 FORTIFY 或隐藏告警。这是确认的代码缺陷，但不是所有低速现象的唯一已证实原因。
- 高性能模式原来只处理 L1SS / LP，没有完整关闭全局 TPO 与各频段 PST。现在同时处理 `PciL1ss`、`TptOption`、`muruLowPwr`、`LpOption`，持久化卡级与两频段配置，检查执行后的真实状态，失败回滚。用户仍可切换标准/高性能模式。
- MT7993 使用的两个普通配置文件中，修正不合法的 `CCKTxStream=4` 为 `2`；不扩大硬件能力或 BA 窗口。
- 保留 2.4 GHz 信道 6、MLO 默认关闭及既有互锁、普通 SSID 的 OWE 路径。TF 的 48 MHz / high-speed 设置保持不变。

本机验证：高性能运行态可读回 L1SS=0、TPO=0、PST=0；没有重启无线。5 GHz 当前为信道 36 / EHT160 / OWE，但测试期间没有持续关联的 5 GHz 客户端，因此没有可报告的吞吐提升百分比。2.4 GHz 客户端信号约 -86 dBm，不能用它评价近距离 Wi-Fi 7 性能。

高性能模式会增加功耗/散热压力。本次温度传感器约 73～81°C，风扇最高 PWM 255、CPU 读回 2 GHz；风扇在本轮运行态改动前就已升至全速。没有完成温度与吞吐的受控 A/B，不能声称此模式在所有负载下都更好。

建议验收时用有线 2.5G 电脑作 iperf3 服务端，Wi-Fi 7 终端固定位置，分别测多流上行、下行；同时保存 `iw dev rai0 station dump`。PHY 协商速率不等于 TCP 吞吐，也不应把未提供有效速率的 MLO 链路算成额外吞吐。

## 2. 内存与长期稳定性

- 仅针对 `nradio,c2000-max`，把两个 PPE 的默认流表从各 32768 项降为各 16384 项。保留原有分配失败降级、公共大小配置与边界处理，不缩减 Wi-Fi WED/RRO 环形缓冲区。
- 按该源码中各表项尺寸计算，预计节省约 5.6 MiB 固定分配；这是估算，尚未在新内核启动后实测。
- 过滤 QModem 热插拔中的 USB 根集线器和接口子事件，避免把 `usb1` / `usb2` 当成模组重复尝试探测。
- 增加只读、单次执行的 `c2000max-netcheck`，没有增加常驻轮询进程。

本机旧内核短时观察：`MemTotal` 491984 KiB，可用内存大致 159～168 MiB，未使用 zram 交换空间；大部分时间 CPU 空闲超过 95%。概览页面登录后连续请求 20 次，全部成功，耗时最小 71.7、平均 73.7、最大 82.0 毫秒。rpcd / uhttpd 的文件描述符分别保持 19 / 9，线程均为 1。

观察窗口内没有发现明显的单调内存增长；这不是“已排除内存泄漏”的证明。对方日志里的超长 collectd 间隔与系统时钟跳变同时出现，不能仅凭该行认定 CPU 死循环。没有对所有可选代理/审计/加速插件同时启用的组合做压力测试。

## 3. 有线 LAN 卡顿

- 本机 eth1 协商 2500 Mbps / 全双工，RX CRC、RX error、TX error 均为 0；电脑到路由器 12 次 ping 均小于 1 ms、无丢包，未复现对方的卡顿。
- 本机 LAN 为 `192.168.66.1/24`，模组上游为 `10.93.3.166/8`，不存在这两者的网段重叠。对方日志也能看到一次 `10.108.97.224` 的模组租约，但无法据此还原其所有 WAN 配置。
- `192.168.0.1` 本身没有问题；只有与实际上游/其他接口地址范围重叠、地址冲突等情形才可能造成相关故障。用户模式和上级网段目前未知，不能认定设备硬件故障或已证明网段冲突。
- 修正首次配置脚本：仅在没有 LAN 地址时设默认值，不再在保留配置升级后强制覆盖用户 LAN IP/掩码。增加 CIDR 重叠诊断，支持不同掩码的检测。
- 保留已经采用的 WAN / 5G+WAN 软件转发加速回退，不重新开启之前造成请求挂起的 WAN HNAT 路径。

请让出现问题的用户在卡顿当时执行 `c2000max-netcheck`，连同当时模式和电脑 IP/网关回传。报告包含接口地址、路由和终端 MAC，公开发布前请脱敏。根据实际结果再区分网段重叠、线材/EEE、USB 网卡、代理、队列或上游问题，不用猜测替换其网络配置。

## 4. 5G NR 游戏延迟

- 把 USB 模组中断从 CPU0 移到 CPU1，与本机活跃的 WED 中断错开；已验证 IRQ affinity 的运行态改变。没有宣称这单项已降低多少 ping。
- 新增 `sqm.nr_game` 预设：接口 `eth2`、CAKE / `piece_of_cake.qos`，默认关闭，上下行均为 0，避免猜测蜂窝容量而意外限速。
- 在“网络 → SQM QoS”中填写实际繁忙时段稳定上下行带宽的约 80%～90%（单位 kbit/s）后再启用。0 表示该方向不整形；不同固件/模组接口名应先核对。
- 启用任意 SQM 队列时暂停硬件/软件流量加速及 C2000MAX 设备限速，保留其配置。禁用 SQM 后，等旧队列拆除再恢复原选择，避免加速绕过队列、两个插件争用 qdisc。启动失败时不会假装已安全启用。
- 没有锁基站、锁频段、强制改 APN、修改模组 NV 或周期性重拨。没有收到容量测量，因此没有在当前路由器启用 SQM，也没有进行满载延迟 A/B。

实机空载参考：经 eth2 到 223.5.5.5 的 12 次 ping 为 17.2 / 75.0 / 163.5 ms（最小/平均/最大），到 119.29.29.29 的 8 次为 20.4 / 25.4 / 38.7 ms；均未丢包。这是不同路径上的短样本，不是优化前后对照。

SQM 针对的是满载排队延迟，不能消除基站调度、覆盖波动或运营商拥塞；蜂窝速率跌到整形值以下时仍可能排队。SQM 与硬件 offload 的冲突以及 CPU 吞吐取舍见 [OpenWrt SQM 官方说明](https://openwrt.org/docs/guide-user/network/traffic-shaping/sqm)。

## 5. 官方 Flash 保护

- 新 DTB 将全部 5 个暴露的 SPI 分区设为只读：U-Boot 环境、Factory、bdinfo、FIP、官方配置区。
- 不再暴露官方 squashfs 的 `firmware` 标签，防止分区探测器把官方 rootfs_data 当成 TF overlay。
- “一次性重启到官方系统”被明确停用；其主入口和遗留返回脚本均不再保留写入实现。因为旧方案需要写官方环境/配置区，不能与本次“不碰官方 Flash”的要求同时保留。
- 回官方请**关机后拔出 TF 卡**再开机；返回 ImmortalWrt 同样关机插卡。不在设备运行时拔卡。
- TF 升级路径仍校验当前 `/rom` 所属 SD、CID 与分区；不能证明目标时拒绝升级，不接受 `/dev/mtd*`。SIM 跨重置记录使用独立 TF 环境分区，实机为 `/dev/mmcblk0p2`，不是 SPI 环境。
- 本轮未运行 `sysupgrade`、SPI 擦写或官方恢复操作。旧镜像保留作为回退文件。

## 6. 验证与交付

已运行：无线高性能切换/失败回滚、MLO 互锁、OWE GCMP256 迁移、旧 LuCI 多设备兼容、SIM 切换、TF 目标绑定升级、SWAP、网口切换/故障注入、低内存服务策略、AT/进程优化、SQM 互斥与恢复、SPI 只读检查。驱动 OWE 测试提取实际修补后的复制分支，对 0～255 的全部 IE 长度执行 ASan/UBSan 与边界哨兵测试。

固件检查包含：最终 DTB 的全部 SPI 只读属性、隐藏官方 firmware 分区、MMC 48 MHz、内核模块 ABI、OWE 补丁、新 LuCI 版本、空 root 密码、SQM 钩子及只读诊断工具。Factory EEPROM 测试因缺少夹具跳过，不能算通过。

IMG 保留既有可启动 TF 引导布局，仅替换新 kernel/rootfs；组装程序校验 GPT、payload 和保留分区哈希。初始 overlay 64 MiB，继续使用首次启动扩容机制；本轮没有对新镜像实际开机扩容做验收。压缩 IMG 和 BIN 用途不同：前者写 TF 卡，后者只用于正在 TF 上运行的 C2000MAX ImmortalWrt 升级，**不要上传到官方系统升级界面**。

交付文件使用前缀 `C2000MAX-V36.5-local-20260905`：原始 IMG、IMG.GZ、sysupgrade BIN、manifest、构建配置、组装记录及 SHA256SUMS。新内核的 Wi-Fi 吞吐、满载游戏延迟和长期稳定性仍需刷入 TF 后验收。
