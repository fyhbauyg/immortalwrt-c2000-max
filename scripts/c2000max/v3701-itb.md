# C2000MAX：ITB 升级包可行性评估

核查日期：2026-09-08。仅评估；没有生成 ITB、执行 make、修改升级/启动代码、访问路由器、提交 Git 或写入任何闪存/TF。

源码基线：WSL Ubuntu-24.04，`/home/wkz/c2000max-v36.01-build`，`763b31f97c72d20376d1ab4b7650651f4a706e2d`（本地 v36.5）。已读用户提供的 `C2000MAX_25.12_6.12_WiFi_HNAT_Codex_2026-09-08.md`；仓库受版本控制文件以及仓库/父目录未找到 AGENTS.md。本文与主任务的 37.01 驱动更新分开，不把驱动更新等同于升级格式迁移。

## 结论

真正的 ITB 可以设计成这个设备的新升级容器，但现有 v36.5 不能直接接收它。当前内核已经是 FIT；当前 sysupgrade BIN 是“tar + OpenWrt 元数据”，包含独立 kernel 与 root。使用 `.itb` 文件名不会自动增加 FIT 内容、rootfs 支持、签名或官方升级兼容性。

建议 37.01 保留现行 BIN 和 TF IMG/IMG.GZ。若以后实现 ITB，应先通过普通 BIN 安装同时支持 BIN/ITB 的过渡版本，并让 ITB 解包后继续写现有 TF 的 kernel/rootfs 两个分区。此方案在设计上不需要改官方 SPI 或改变 U-Boot 启动方式；是否正确必须由实现后的镜像校验、故障模拟与实机验收证明。

不能仅将 C2000MAX 的检查器改成 `fit_check_image`：现有通用 FIT 写入器会把整个 FIT 写到 kernel 分区，不会分离 rootfs。这与 MAX 的固定 32 MiB kernel 分区及独立 rootfs 挂载方式不兼容。

## 四种不同含义

| 方案 | 实际内容与用途 | v36.5 原样接收 |
|---|---|---|
| 内核 FIT/ITB | 压缩内核 + DTB；不含持久 rootfs。当前 kernel 成员已是此格式 | 不能作为完整升级包直接接收；它是现有 tar 内部成员 |
| 带 rootfs 的真实 ITB | FIT 包含 kernel、DTB、filesystem 等子镜像；还必须定义 MAX 的检查、提取和分区写入规则 | 否，需先升级接收端 |
| BIN 仅改名 ITB | 字节仍为 tar + metadata | 内容层面的现有检查仍可能通过，但它不是 ITB；无格式迁移价值，不建议发布这种命名 |
| NRadio 官方系统升级包 | 官方升级器自己的包头、机型、签名、分区与安装规则 | 未验证，也没有足够公开/本地证据证明兼容；BIN、IMG、拟议 ITB 均不得因此称作官方升级包 |

U-Boot 的 FIT 是多子镜像容器，`bootm` 按配置选取内核、设备树和可选 ramdisk；支持 FIT 启动不等于支持某个设备的系统升级协议。[U-Boot FIT 文档](https://docs.u-boot.org/en/latest/usage/fit/index.html)、[bootm 文档](https://docs.u-boot.org/en/latest/usage/cmd/bootm.html)。OpenWrt 的 `mkits.sh` 明确分别处理 initrd 和 rootfs，rootfs 为 `filesystem` 子镜像；SquashFS 持久 rootfs 不能仅换成 ramdisk 属性就视为完成适配。[OpenWrt mkits.sh](https://github.com/openwrt/openwrt/blob/main/scripts/mkits.sh)

该组装器 `:121` 明确保留已有 primary-only GPT 约定；常规升级只替换 kernel/rootfs，不重分区。

本次只读检查已有 `c2000max-artifacts-v365/C2000MAX-V36.5-local-20260905-sysupgrade.bin`：tar 内 kernel 为 5,929,180 字节，root 为 96,651,264 字节（约 92.17 MiB），root 单独就超过 kernel 分区 32 MiB。对应 IMG 的 rootfs 分区 163,774,464 字节，overlay 起点 96,665,600 字节，初始预留 64 MiB。原始数字亦记录于工作区 `C2000MAX-V36.5-local-20260905-assembly.txt`。

不能将上述名为 fip/env 的 TF 分区误说成有效 TF 引导器：该已有 IMG 的 2 MiB fip SHA-256 为 `5647f05ec18958947d32874eeb788fa396a05d0bab7c1b71f112ceb7e9b31eee`，与等长全零数据一致；512 KiB env 的 `07854d2fef297a06ba81685e660c332de36d5d18d546927d30daad6d7fda1541` 也与全零一致。

工作区已有 `tools/c2000max-spi-fip-reader/c2000max-u-boot.bin` 可读到 `U-Boot 2025.01-rc4 (May 21 2025 - 03:18:44 +0000)`、`loadaddr=0x48000000`、`bootdelay=2`，以及 `boot_from_sd` 和 SD 失败后回退 flash 的提示字符串。结合空白 TF FIP，这支持“已有启动依赖设备自身 SPI 引导链”的推断；这些字符串不是完整控制流或实际设备当前环境的证明。本次未获得可与该二进制精确对应的 MAX U-Boot 源码/defconfig，也未读取实时 bootcmd、加载长度、外部 FIT 数据处理或签名策略。

因此不能承诺该 U-Boot 会直接启动包含整个 rootfs 的新 ITB。保留现有内核 FIT 字节及 GPT 布局，可以避免因升级包装变化而新增 bootloader 依赖。若改成单分区 FIT/fitblk，则还需要核实 U-Boot 读区间、RAM 地址范围、rootdisk/fitblk 接线、内核命令行、GPT 与 overlay；这已超出本次兼容包装方案。

## 可实施但尚未实施的路线

### A. ITB 只作升级容器，保留双分区启动（建议未来方向）

1. 在 `filogic.mk` 增加一个并行产物，保留 `sysupgrade.bin`。明确定义容器版本、`nradio,c2000-max`、默认配置、payload 名称和校验算法。可把“原样内核 FIT”和“原样 SquashFS”作为两个载荷，以便取出的 kernel 字节仍可由旧启动链使用；这种外层 ITB 是升级容器，不应冒充可被现有 U-Boot 直接 bootm 的启动镜像。
2. 在 MAX 专属升级代码添加严格读取/提取器，完整检查 FDT/FIT 结构、唯一载荷与引用、长度、对齐、外部 data offset/position 范围、重叠/截断、机型/版本、kernel FIT 和 SquashFS 格式及载荷 hash。标准 flat FIT 方案若需要重新构造 kernel-only FIT，必须额外验证重建结果、工具依赖及旧 U-Boot 支持，复杂度高于保留原样 kernel。
3. `platform_check_image` 同时支持原有 tar 和明确定义的新 ITB；继续执行 fwtool 元数据检查。写入前完成所有载荷及尺寸检查，禁止用 `-F` 代替迁移逻辑。默认 FIT 魔数通过不代表合格的 MAX 完整系统包。
4. 新增专用分区写入路径，不能让外层 ITB 落入现有 `emmc_upgrade_fit()`。保持 `/rom → SD CID + 设备号 + GPT 名称` 绑定；仅写这张 TF 的 kernel/rootfs。写前分别检查 32 MiB kernel 上限、rootfs 容量、overlay 余量；显式处理提取/写入错误和读回核验，验证失败不自动重启。
5. 保留配置和不保留配置两条分支都应计算相同的 64 KiB overlay 边界，正确清理旧 F2FS 两份 superblock。新工具和依赖必须进入 stage2 RAMFS；512 MiB 设备应控制上传包与提取缓存峰值，尽量流式处理，不能无限复制整包。
6. 同步扩展 `assemble-c2000max-sdcard.py`、元数据/固件检查脚本与发布记录，并确保 BIN 与 ITB 提取出的 kernel/rootfs 字节相同。IMG 应继续保留可恢复用途，不把 ITB 当作能直接写整张卡的磁盘镜像。

FIT 支持内联/外部载荷，但引用和范围必须由消费端正确实现；更换格式不会自动建立可信签名链。[FIT 规范](https://fitspec.osfw.foundation/#external-data)、[U-Boot FIT 签名说明](https://docs.u-boot.org/en/latest/usage/fit/signature.html)。hash 提供内容完整性检查，身份认证还需要受信密钥、签名策略及实际强制验证，不能因出现 hash 或 `fit_check_sign` 名称便宣称已实现安全启动。

### B. 整个 kernel + rootfs FIT 写进一个分区（不建议本轮采用）

需要变更分区容量或采用新的整体 firmware/rootdisk 布局，并调整引导、FIT 块设备、rootfs/overlay 挂载和升级恢复逻辑。现有 GPT kernel 只有 32 MiB，当前 rootfs 已超过此上限；只改 `IMAGE/sysupgrade.itb` 或检查函数无法完成。这会破坏旧版本的分区假设，需要单独迁移版本和恢复计划；若方案要求修改官方 SPI，则与本任务约束不符。

## 升级与回退兼容性

| 起点 → 目标 | 条件与限制 |
|---|---|
| 原始 v36.5 → 当前 37.01 BIN | 沿用现有 tar + metadata 与 GPT 布局时，格式层面兼容；新驱动/配置行为仍需独立验收 |
| 原始 v36.5 → 真 ITB | 不兼容；新镜像内的接收器尚未安装，无法让旧系统在首次升级时自动认识新格式 |
| v36.5 → 过渡 BIN → ITB | 可行设计；过渡 BIN 必须真正包含双格式接收器，并在后续 ITB 交付前验证 |
| 已支持 ITB 的新系统 → v36.5 BIN | 若始终保留双分区布局及 tar 接收能力，镜像格式可回退；配置兼容单独判断，必要时不保留配置 |
| 回退到 v36.5 后再次升级 ITB | 又会失去 ITB 接收能力，需要再次经过桥接 BIN |
| 新单分区 FIT 布局 → 旧 v36.5 BIN | 无法假定兼容；旧脚本要求独立 kernel/rootfs，不能直接提供普通回退承诺 |
| 官方系统 → 任一上述包 | 未建立兼容路径，不纳入支持范围 |

后缀、FIT payload hashes、fwtool 兼容版本是不同层次。若只新增容器而不改变磁盘/配置布局，可使用专属容器版本表达接收能力；若改变布局，则应明确设备兼容版本与迁移限制，不应靠关掉校验绕过。

## 官方 SPI 保护与验证边界

设备树 `mt7987a-nradio-c2000-max.dts:357`、`:386`–`:417` 将公开的 u-boot-env、Factory、bdinfo、FIP、factory-overlay 设为只读，并不暴露官方 firmware/rootfs 分区。`package/custom/c2000max-board/files/usr/sbin/c2000max-boot-official-once:1` 已取消原先写官方环境/配置的实现；遗留 `.../usr/lib/c2000max/official-return-tf:1` 也直接拒绝执行。ITB 功能不应增加 SPI 写入、引导器更新、Factory 替换或恢复这些入口。

这些是当前内核/软件路径上的保护，不是能够约束其他内核、U-Boot 命令或外部编程器的硬件写保护。本次只检查已有本地文件；没有读取当前设备、运行 `sysupgrade -T`、烧录、启动新镜像或验证断电恢复。当前实现没有双系统 A/B 提交机制，容器换成 ITB 本身也不会使 TF 原地升级具有断电原子性。

未来实现至少需要验证：旧 BIN、新 ITB、错误机型、缺载荷、重复引用、hash 错误、外部数据越界/截断、超大载荷、非当前 SD/CID 改变、提取/写入/读回故障、保留及不保留配置、RAM 使用峰值、回退 BIN 和实机冷启动。以上为待做验收，不是本次已通过项目。

本次直接访问 OpenWrt 文档站时遇到站点机器人验证页，因此使用 OpenWrt 官方源码仓库作为升级实现的一手来源；没有把验证页面当作文档内容。所有一手 URL 的核查日期均为 2026-09-08，`main`/`latest` 后续可能变化，本地 C2000MAX 结论以本文固定基线及列明代码为准。
